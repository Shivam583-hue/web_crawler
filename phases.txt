Phases
Phase 1 — Sequential Crawler (no concurrency)
Goal: Get the pipeline working end-to-end before adding concurrency complexity.

HTTPClient module wrapping :httpc or Req
Parser module using Floki to extract <a href> links
A simple recursive function: crawl(url, visited, depth)
No supervision tree yet — just pure functions

This gives you a working crawler you can test against a local server.

Phase 2 — Queue GenServer
Goal: Extract state into a proper GenServer so workers can share it safely.
elixir# Public API
Queue.enqueue(url)
Queue.dequeue()        # returns {:ok, url} | :empty
Queue.mark_visited(url)
Queue.visited?(url)

Internal state: %{frontier: :queue.new(), visited: MapSet.new()}
dequeue is a call (not cast) — same lesson as your KV store, you need the return value synchronously
enqueue can be a cast since you're fire-and-forget


Phase 3 — Task-based Worker Pool
Goal: Spawn concurrent workers that pull from the Queue.

A WorkerPool module that spawns Task.async workers up to a max concurrency limit (e.g. 10)
Each task: dequeue a URL → fetch → parse links → enqueue new links → report results back
Use Task.async_stream or manual Task.Supervisor depending on how much control you want
Workers report results back via send to a coordinator, or you collect with Task.await


Phase 4 — DynamicSupervisor + Rate Limiter
Goal: Make it production-safe and polite.

Wrap the pool under a DynamicSupervisor so crashed workers are isolated
Add RateLimiter GenServer: token bucket per domain — workers ask permission before fetching
Add configurable depth limit and max pages
Full supervision tree under CrawlerSupervisor


Phase 5 — Observability & Output
Goal: Make results useful.

Stream results to a CSV or ETS table as crawl progresses
Track stats: pages crawled, errors, avg response time
Optional: a simple CrawlerStats GenServer that aggregates telemetry

Phase 4: Rate Limiter
│
├── [ ] 1. Create Crawler.RateLimiter
│         use GenServer
│         State: %{buckets: %{}}
│         Each bucket: %{tokens: float, last_refill: integer}
│         Config (module attrs): 
│           @capacity 5        ← max tokens per domain
│           @refill_rate 1.0   ← tokens per second
│           @min_wait_ms 200   ← returned when denied
│
├── [ ] 2. Public API
│         start_link(_opts)
│         check_and_consume(domain) ← call, returns :allow | {:deny, wait_ms}
│
├── [ ] 3. handle_call for check_and_consume
│         Get or initialize bucket for domain
│         Compute elapsed since last_refill using System.monotonic_time(:millisecond)
│         Refill: new_tokens = min(@capacity, current + elapsed * @refill_rate / 1000)
│         If new_tokens >= 1.0 → reply :allow, store tokens - 1.0, update last_refill
│         Else → reply {:deny, @min_wait_ms}, store refilled amount, update last_refill
│
├── [ ] 4. Private helper — get_or_init_bucket(buckets, domain)
│         If domain exists → return existing bucket
│         If not → %{tokens: @capacity, last_refill: System.monotonic_time(:millisecond)}
│         This is where new domains get a full bucket on first visit
│
├── [ ] 5. Add RateLimiter to supervision tree
│         Crawler.Supervisor children:
│           [Crawler.Queue, Crawler.WorkerPool, Crawler.RateLimiter]
│         Register under name: __MODULE__ so workers reach it without pid passing
│
├── [ ] 6. Update Crawler.Worker
│         Add fetch_with_rate_limit(url) private function
│         Extract domain via URI.parse(url).host
│         Call RateLimiter.check_and_consume(domain)
│         On :allow → Http.fetch(url)
│         On {:deny, wait_ms} → Process.sleep(wait_ms), retry
│         Replace Http.fetch call in process/3 with fetch_with_rate_limit
